# Historical data import plan

Read `docs/Catalog FSD.xlsx` and modify `docs/free-spirit-dance-import.sqlite` directly. Do not generate intermediate attendance-review or import workbooks. Validate the SQLite changes before synchronizing the separate Catalog development database or preparing any production transfer.

1. **Read the source catalog.** The prepared database includes both courses from January 9, 2024; the user authorized earlier Intermediates classes before the previously recorded September 26 start. The schedule change takes effect May 21, 2026 for both courses. Beginners currently meets Thursday 20:00–21:20; Intermediates Tuesday 20:00–21:20. Before the change, both met Tuesday and Thursday: Beginners 19:00–20:00 and Intermediates 20:00–21:00. Preserve catalog dates with recorded attendance, including exceptions to the weekly schedule; blank cells do not establish attendance or enrollment.
2. **Apply direct SQLite corrections.** Back up the database, validate fields and references, preserve existing IDs and unrelated data, deduplicate by student/course/date, retain source-cell references, and write transactionally. `p`/`pc` mean present; `a`/`am` mean absent. Historical payments have amount zero and cover both courses. Final payment coverage remains unresolved unless clarified. Only payment-covered missed classes belong in visible activity logs; do not infer absences during inactive gaps.
3. **Import in dependency order.** Courses and schedules → held/cancelled classes → students and course assignments → payments and course allowances → attendance. Include payment methods, receiving administrators, school handover status, complimentary attendance, and rent records where available. Include practice parties/donations and opening credits if needed.
4. **Validate locally.** Ensure current schedules do not generate incorrect historical calendar entries. Check duplicates, cancelled classes, row counts, payment totals, student balances, and sample profiles. Run `npm run build` for any application changes.
5. **Prepare production transfer.** Decide replacement versus merge based on existing production data. Generate SQL compatible with production migrations, preserving relationships and administrator settings; map conflicting IDs for a merge. Handle required historical administrator references and transfer images separately to R2.
6. **Load and verify production.** Back up production data and affected images, prepare a rollback procedure, and obtain approval for the concrete transfer before execution. Prevent concurrent edits during transfer, then compare counts, totals, balances, and representative profiles with local results.

Keep workbooks, database dumps, and student images outside Git. An XLSX export contains image references, not image backups.
